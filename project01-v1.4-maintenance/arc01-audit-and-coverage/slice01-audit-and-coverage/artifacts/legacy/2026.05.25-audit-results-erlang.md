## Executive Summary

iso8601 is a small, focused, well-tested parsing library with 100% line coverage
and a clean dialyzer/xref gate. The dominant cluster of issues is **leftover debug
I/O** (`io:format` in production paths — two calls), **ignored duration sign** (the
parsed sign field is discarded in `apply_duration/2`, so negative durations are
applied as positive), and **unused macros** (`?MIDNIGHT`, `?NOON`, `?TEATIME`).
OTP-compatibility analysis confirms no post-OTP-17 syntax or BIFs are used; the
floor holds. No architecture document exists beyond CLAUDE.md.

## Findings

### Correctness / Soundness

#### F-1: `apply_duration/2` ignores the parsed sign

**Severity:** High
**Location:** `src/iso8601.erl:159`
**What's wrong:** The `sign` field from `parse_duration/1` is matched as `_S` and
never applied. A duration string `"-P1Y"` (negative) is applied identically to
`"P1Y"` (positive).
**Why it's wrong:** A caller who passes a negative ISO 8601 duration (legal per the
spec) gets the wrong datetime — time is added instead of subtracted. This is a
silent correctness bug for anyone using signed durations.
**Fix:** At `src/iso8601.erl:159`, negate the component values when `Sign` is `"-"`:

```erlang
apply_duration(Datetime, Duration) ->
    [{sign, Sign}, {years, Y}, {months, M}, {days, D},
     {hours, H}, {minutes, MM}, {seconds, SS}] = parse_duration(Duration),
    F = case Sign of "-" -> fun(X) -> -X end; _ -> fun(X) -> X end end,
    D1 = apply_years_offset(Datetime, F(Y)),
    D2 = apply_months_offset(D1, F(M)),
    D3 = apply_days_offset(D2, F(D)),
    apply_offset(D3, F(H), F(MM), F(SS)).
```

#### F-2: `apply_years_offset/2` produces invalid dates (e.g. Feb 29 in non-leap year)

**Severity:** High
**Location:** `src/iso8601.erl:451-453`
**What's wrong:** Adding years to a Feb 29 date naively constructs `{Y+AY, 2, 29}`
which may be invalid (non-leap year). Unlike `apply_months_offset` which calls
`find_last_valid_date/1`, this function doesn't validate.
**Why it's wrong:** `calendar:valid_date({2017, 2, 29})` returns `false`;
downstream code using this datetime (e.g. `calendar:date_to_gregorian_days/1`)
will crash or produce wrong results. `add_years({{2016,2,29},{0,0,0}}, 1)` returns
`{{2017,2,29},{0,0,0}}` — an impossible date.
**Fix:** Wrap the result in `find_last_valid_date/1`:

```erlang
apply_years_offset(Datetime, AY) ->
    {{Y, M, D}, {H, MM, S}} = Datetime,
    find_last_valid_date({{Y + AY, M, D}, {H, MM, S}}).
```

#### F-3: Debug `io:format` calls in production parse path

**Severity:** High
**Location:** `src/iso8601.erl:185`, `src/iso8601.erl:189`
**What's wrong:** Two `io:format/1,2` calls emit debug text to stdout on every
ordinal-date parse.
**Why it's wrong:** Library callers will see unexpected output on stdout. In a
supervised system this pollutes logs; in an embedded device or test harness it
causes noise or flaky assertions. This is OPS-01 (no `io:format` debugging in
production) and TE-13 (no test scaffolding in src).
**Fix:** Delete both lines entirely.

#### F-4: `gi/1` silently converts parse failures to 0

**Severity:** Medium
**Location:** `src/iso8601.erl:114-119`
**What's wrong:** `gi/1` returns `0` when `string:to_integer/1` fails. This is
called on regex-captured groups that are empty strings (intentional — the regex
group didn't match), but `gi` cannot distinguish "group didn't match" from "group
matched garbage." If the regex were ever relaxed or a bug introduced, the 0
fallback would silently corrupt the result.
**Why it's wrong:** This is defensive programming (AP-07) — converting a parse
failure into a sentinel value rather than crashing. The current regex guarantees
only digit strings reach `gi`, so the `error -> 0` branch only fires for empty
captures. It works today but violates the let-it-crash contract: a real error would
be invisible.
**Fix:** Rename to clarify intent and make the fallback explicit for the empty-string
case only:

```erlang
gi("") -> 0;
gi(DS) -> list_to_integer(DS).
```

This crashes on actual garbage (correct) and returns 0 for empty captures (the
intended semantics).

### OTP Compatibility

#### F-5: `calendar:now_to_datetime/1` deprecated since OTP 18

**Severity:** Medium
**Location:** `src/iso8601.erl:49,56,63,70,85`
**What's wrong:** `calendar:now_to_datetime/1` has been deprecated since OTP 18.
It still *works* on OTP 20-27 (not removed), but generates deprecation warnings
on newer compilers when `warnings_as_errors` is enabled.
**Why it's wrong:** The function accepts `erlang:now()` tuples which are themselves
deprecated. Users on modern OTP are nudged toward `erlang:timestamp()` and
`calendar:system_time_to_universal_time/2`. Since this is a public API, removing
it is a breaking change — but it should be flagged for future deprecation.
**Fix:** No immediate code change required (the function still exists through
OTP 27). Flag for the next major version: deprecate the `{MegaSecs, Secs, Micro}`
clauses and direct callers to convert before calling. Alternatively, keep them
but replace `calendar:now_to_datetime/1` with an equivalent private
implementation using `calendar:gregorian_seconds_to_datetime/1`.

**Location:** entire `src/iso8601.erl`
**What's wrong:** Nothing — all BIFs and stdlib calls used have been available since

### Idioms / Style

#### F-7: Unused macros `?MIDNIGHT`, `?NOON`, `?TEATIME`

**Severity:** Low
**Location:** `src/iso8601.erl:16-18`
**What's wrong:** Three macros are defined but never referenced anywhere in `src/`.
`?V` is used; the other three are dead definitions.
**Why it's wrong:** Dead code clutters the module and misleads readers into thinking
these values matter to the implementation. xref doesn't catch unused macros.
**Fix:** Delete lines 16-18.

---

#### F-8: `?V` macro wraps a function call (ID-14 / AP-23)

**Severity:** Low
**Location:** `src/iso8601.erl:19`
**What's wrong:** `-define(V, proplists:get_value).` is used as a code macro —
`?V(key, List)` expands to `proplists:get_value(key, List)`. This is the
"macros for code" anti-pattern (AP-23 / ID-14): the expansion is opaque to tools,
can't be traced, and hides the actual function being called.
**Why it's wrong:** A reader seeing `?V(hour, Plist, 0)` must know the macro
definition to understand the code. It also prevents grep from finding
`proplists:get_value` call sites directly. Dialyzer still analyses it (since the
preprocessor expands before analysis), so this is a readability issue rather than
a correctness issue.
**Fix:** Replace all `?V(...)` occurrences with `proplists:get_value(...)` and delete
the macro definition. The resulting code is only slightly longer and self-documenting.

---

#### F-9: `gi/1` is exported (appears in xref as used) but has no edoc, cryptic name

**Severity:** Low
**Location:** `src/iso8601.erl:112-119`
**What's wrong:** The function name `gi` is opaque (stands for "get integer" per the
comment), the `%doc` comment is malformed (missing a `%`), and the spec claims it
returns `integer()` but it can return `0` for non-integer input — the spec doesn't
convey the fallback semantics.
**Why it's wrong:** Violates ID-19 (principle of least astonishment) and ID-01
(naming). A private helper with a one-letter name isn't navigable. The malformed
comment won't be picked up by edoc.
**Fix:** Rename to a descriptive name (e.g. `capture_to_integer`), fix the `%%`
comment prefix, and simplify per F-4 above.

#### F-10: Tests use `?assertMatch` where `?assertEqual` is computable

**Severity:** Low
**Location:** `test/iso8601_tests.erl` (throughout — ~100 uses)
**What's wrong:** Nearly all assertions use `?assertMatch` to compare a fully
concrete expected tuple against the result, e.g.
`?_assertMatch({{2012,1,1},{0,0,0}}, F("2012"))`. Since both sides are ground
terms, `?assertEqual` would give a stricter check (symmetrical comparison) and
more informative failure messages.
**Why it's wrong:** `?assertMatch` only checks that the result *matches* the
pattern (LHS); extra structure in the result won't fail. For ground terms this
distinction is moot, but the weaker assertion is a habit that could mask bugs if
patterns with wildcards slip in. Per TE-02, use the strongest assertion that fits.
**Fix:** Mechanical replacement: `?_assertMatch(Expect, Expr)` →
`?_assertEqual(Expect, Expr)` wherever `Expect` is fully ground. Leave
`?assertMatch` only where wildcards or `_` are genuinely needed (e.g. the
`parse_duration` tests that use `[{sign,[]},{years,1}|_]`).

### Performance

#### F-11: `proplists:get_value/2,3` is O(n) per lookup; accumulator is scanned repeatedly

**Severity:** Low
**Location:** `src/iso8601.erl:362-369` (the `datetime/1` function)
**What's wrong:** The `datetime/1` function calls `proplists:get_value` seven times
on the same proplist (hour, minute, second, offset_sign, offset_hour,
offset_minute, second_decimal). Each call is O(n) on the accumulator list.
**Why it's wrong:** For this library's use case (small proplists, ~7 keys max), the
practical impact is negligible — total overhead is maybe 50 list traversals per
parse. This is not a performance bug; noting it only because a reviewer would
wonder. A map would be O(1) per access but would be a larger refactor.
**Fix:** No fix needed at current scale. Flag as an open question for a future
refactor if profiling ever shows parsing as a bottleneck.

7. **Binary/atom table leaks from user input (AP-01/AP-02):** Not applicable —
   input is char-list strings only; no `binary_to_term`, no atom construction.
