## Findings

### ERL-DATE-001 — ISO week parser normalizes out-of-range week/day fields instead of rejecting them

**Severity: Medium.** The parser silently maps invalid week representations onto different valid calendar dates, so a caller can ingest a malformed date as a plausible but different one.

**Location and cause:** `src/iso8601.erl:257–282` parses week and weekday digits without range checks. `make_date/4` calculates a linear hour offset from any parsed numbers and `apply_offset/4` normalizes it through Gregorian seconds (`471–475`, `491–500`). The exported helper spec calls the week `pos_integer()` (`456–462`), but the parser allows zero and no validation checks the year's actual 52/53-week limit.

**Reproduction:** Run `artifacts/date-probes.escript` on the fresh beam. `parse("2014-W00-1")` returned `{{2013,12,23},{0,0,0}}`; `parse("2014-W53-1")` returned `{{2014,12,29},{0,0,0}}`; `parse("2014-W01-8")` returned `{{2014,1,6},{0,0,0}}`. These fields should be rejected: OTP 18's calendar documentation defines `weeknum()` as `1..53`, `daynum()` as `1..7`, and describes `iso_week_number/1` as ISO-conforming ([OTP 18 calendar manual](https://www.erlang.org/docs/18/man/calendar.html), lines 1404–1439). For the year-specific case, `calendar:iso_week_number({2014,12,29})` returned `{2015,1}`, confirming the invalid `2014-W53-1` aliases the valid `2015-W01-1` call, which also returned 2014-12-29.

**Controls:** Valid `parse("2009-W53-7")` returned `2010-01-03`; valid `parse("2015-W01-1")` returned `2014-12-29`; the assignment's `2009-W01-1` positive control returned `2008-12-29`. Existing tests cover valid week forms and weekday-start-year branches (`test/iso8601_tests.erl:29–47`, `398–410`) but do not exercise invalid field ranges.

**Expected / actual:** Expected rejection of week zero, weekday outside 1–7, and week 53 when that ISO year has only 52 weeks; actual is successful calendar normalization. Confidence high. Recommendation for a future authorized repair: validate parsed week/day and year-specific week count before converting to an offset. No source repair was authorized here.

### ERL-DATE-002 — Expanded years below 1 bypass calendar-date validation

**Severity: Medium.** `parse_expanded/1` accepts impossible dates for year zero and negative years, allowing malformed external date data to pass as a successful `expanded_datetime()`.

**Location and cause:** `make_date/4` constructs `{Year, Month, Day}` directly for calendar-form dates (`src/iso8601.erl:468–470`). `apply_offset/4` returns that tuple unchanged for `Y < 1` and zero rounded offset (`497–505`), bypassing the Gregorian calendar conversion that validates positive-year date tuples. Offset rejection for years `<= 0` is documented in README and EDoc and supported by archived design-history evidence; that intentional behavior is not this finding.

**Reproduction:** `parse_expanded("-0001-02-29")`, `"-0001-02-30"`, `"-0001-13-01"`, `"-0001-01-00"`, and `"-0000-02-30"` all returned tuples instead of an error. The `-0001-02-29` result is invalid under Gregorian arithmetic because astronomical year -1 is not divisible by four; year zero is a leap year, so `-0000-02-29` is a valid control while `-0000-02-30` is not. OTP 18 calendar documentation says the calendar uses Gregorian rules, extends them back through year zero, and requires date tuples to denote valid dates ([OTP 18 calendar manual](https://www.erlang.org/docs/18/man/calendar.html), lines 1404–1418, 1643–1651). The repository describes `parse_expanded/1` as parsing ISO strings with negative astronomical years (README 166–192; EDoc `src/iso8601.erl:138–142`), so expanded years retain the date-validity contract.

**Controls:** Valid `parse_expanded("-0001-01-01")`, `parse_expanded("-0004-02-29")`, and `parse_expanded("-0000-02-29")` succeeded. Ordinary `parse("2017-02-30")` raised `error:if_clause`; its regression test explicitly expects an error for an out-of-range positive date (`test/iso8601_tests.erl:1043–1047`). Valid `2016-060` ordinal parsing still returns February 29 (`196–220`; public probe confirmed it).

**Expected / actual:** Expected rejection of invalid month/day combinations for every expanded Gregorian year, using the same proleptic leap rule; actual returns the unchecked date tuple when `Y < 1` and there is no nonzero offset. Confidence high. Recommendation for a future authorized repair: validate date fields independently of UTC-offset conversion, using proleptic Gregorian arithmetic that handles astronomical years. No source repair was authorized here.

### ERL-DATE-003 — Six-place float formatting can round into second 60 without carrying the date/time

**Severity: Medium.** A valid float-seconds value just below the minute boundary can produce a timestamp that is not valid for the represented UTC date, and parsing that output changes it to the next day.

**Location and cause:** Both float clauses format seconds directly with `~9.6.0f` and do not normalize a rounded `60.000000` (`src/iso8601.erl:101–104`, `112–115`). The `datetime()` types accept `second() | float()` (`40`, `53–54`); the exported `second()` range is `0..59` (`38`). README promises microsecond precision via rounding (`README.md:51–53`), while EDoc promises an ISO-8601 representation (`src/iso8601.erl:96–98`, `110–112`).

**Reproduction:** On an ordinary UTC date, `format({{2012,12,30},{23,59,59.9999994}})` returned `<<"2012-12-30T23:59:59.999999Z">>`, but changing only the fraction to `59.9999999` returned `<<"2012-12-30T23:59:60.000000Z">>`. Parsing the latter returned `{{2012,12,31},{0,0,0}}`. `format_expanded({{-1,12,30},{23,59,59.9999999}})` likewise emitted `-0001-12-30T23:59:60.000000Z`. NIST's UTC table lists the 2012 leap-second insertion at June 30, not December 30 ([NIST leap-second table](https://www.nist.gov/pml/time-and-frequency-division/time-realization/leap-seconds), table lines 152–173); IERS explains leap seconds are inserted at month-end ([IERS Bulletin C metadata](https://datacenter.iers.org/productMetadata.php?id=16)). The test date cannot treat this `60` as an actual leap second.

**Controls:** The immediately lower fraction formats as `59.999999`; the prompt's format epoch control returns `<<"1970-01-01T00:00:00Z">>`; an ordinary `.5` value returns `...06.500000Z` and the existing EUnit float case passes (`test/iso8601_tests.erl:305–308`).

**Expected / actual:** With round-to-nearest microsecond, expected carry to `2012-12-31T00:00:00.000000Z` (and the corresponding next date in expanded formatting), or a documented/rejected boundary policy; actual emits second 60 for a date without a leap second and subsequent parse normalizes to the next day. Confidence medium-high. Recommendation for a future authorized repair: normalize the rounded integer microseconds across seconds/minutes/days before rendering, with explicit leap-second policy if the library intends to support one. No source repair was authorized here.

### ERL-DATE-004 — Three `iodata()` parse specs overstate accepted nested input shapes

**Severity: Low.** Callers relying on the declared input type can pass valid nested iodata and receive `badarg`; ordinary flat strings and binaries work.

**Location and cause:** `parse/1`, `parse_exact/1`, and `parse_expanded/1` each declare `iodata()` (`src/iso8601.erl:121`, `129`, `138`). Each converts binaries to flat lists, but passes every other value directly into parser clauses that expect a flat list of character integers (`123–147`, `236–388`). The README and EDoc use “string” and binary examples rather than documenting nested iodata (`README.md:73–108`; EDoc `122–142`), so this is a declared-type/prose mismatch rather than a claim that every prose example fails.

**Reproduction:** The runner passes valid nested-iolist inputs such as `["2012-02-16", [$T, "01:06:48Z"]]` to each ordinary/exact/expanded parser; all three raise `error:badarg`. The full output records the corresponding exact inputs.

**Controls:** Flat string `"2012-02-16"` and binary `<<"2012-02-16">>` both return `{{2012,2,16},{0,0,0}}`; binary `parse_exact(<<"20120203T040506.50">>)` returns the documented `{4,5,6.5}` shape; expanded binary parsing is covered by EUnit (`test/iso8601_tests.erl:315–323`, `957–977`). The spec is the basis for caller-valid nested input; OTP defines `iodata()` as `iolist() | binary()` and demonstrates nested list/binary members ([OTP 18 erlang manual](https://www.erlang.org/docs/18/man/erlang.html); [OTP 24 erlang manual](https://www.erlang.org/docs/24/man/erlang.html)).

**Expected / actual:** Expected the declared `iodata()` shapes to parse identically to their flattened bytes; actual rejects nested lists. Confidence medium because EDoc/README examples are narrower than the type spec. Recommendation for a future authorized change: either normalize iodata before parser dispatch or narrow all three public specs and documentation consistently, preserving the chosen input contract. No source repair was authorized here.

The audit covers date and date-time parse/format contracts only. Duration fractional truncation remains documented and outside this scope; repeated intervals and basic expanded format remain documented exclusions. The source is unchanged, so this report proposes no repair. Invalid week component expectations are supported by OTP 18's ISO-conforming calendar docs and independent OTP28 week conversion; negative/zero-year date validity is supported by Gregorian calendar documentation and the repository's expanded-year contract. The nested-iodata item is a Low finding because the source specs are broader than user-facing prose examples.
