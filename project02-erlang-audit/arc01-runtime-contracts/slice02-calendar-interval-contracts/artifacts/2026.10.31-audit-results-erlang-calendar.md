## Executive summary

The remaining ten public APIs were traced through their shared arithmetic, duration, and interval helpers. Four Medium findings are supported by fresh public-API probes: month/year clamping can recurse indefinitely below the installed calendar’s year range; duration composition crashes on a fractional-second datetime accepted by the module’s `datetime()` type; interval classification/truncation mishandles explicit positive expanded years; and abbreviated time-only endpoints omit the starting endpoint’s explicit zone. The last finding is grounded in the repository’s documented abbreviated-component behavior and preserved resolved design intent, not an independent ISO conformance claim.

One nearby candidate was dispositioned without a finding: a zoned start written at minute precision fails in the underlying timestamp parser before interval inheritance runs. The repository does not promise this reduced-precision-plus-offset form in its current examples/tests, so this slice records the rejection and its separate parser path without expanding scope into a standards-based parser audit. Another retained type issue is Slice01’s `parse_exact/1` calendar-return declaration despite fractional-second output; it remains an Arc02 obligation, not a fifth Slice02 finding.

Fresh focused probes ran against a newly compiled beam from the pinned source on OTP28. No full native gates were rerun: the source/config/dependency/runtime identity is unchanged, and accepted Slice01 OTP28 gate results were previously independently reproduced by CDC. This does not establish OTP20–27 or R15B03 behavior.

## Findings

### ERL-CAL-001 — Month/year clamping does not terminate below calendar year zero

**Severity: Medium.** A valid year-1 input with an integer negative month/year adjustment crossing below year zero leaves the caller in unbounded recursion, rather than completing or failing in bounded time. The triggering boundary is narrow, but the synchronous API can consume a caller process indefinitely.

**Location and cause:** `src/iso8601.erl:509–522` constructs the adjusted year/month; `537–542` recursively decrements only the day while retaining the same year and month. The installed OTP28 `calendar:valid_date/1` at `/opt/homebrew/Cellar/erlang/28.1.1/lib/erlang/lib/stdlib-7.1/src/calendar.erl:862–883` returns false for all years below zero (`valid_date1` requires `Y >= 0`). Therefore when the adjusted year is negative, no day value can make that date valid and the recursive state never changes year/month. The shared path is also reached by `apply_duration/2` and interval bound resolution.

**Scale:** logical arithmetic/duration unit, affecting `add_years/2`, `add_months/2`, and composed duration/interval calls.

**Public reproduction:** `add_years({{1,1,1},{0,0,0}},-2)`, `add_months({{1,1,1},{0,0,0}},-24)`, `apply_duration({{2017,1,1},{0,0,0}},"-P9999Y")`, and `interval_bounds(parse_interval("0001-01-01/-P2Y"))` were each executed in a monitored child with 250 ms timeout, `kill`, and confirmed monitor `DOWN`; each timed out. No potentially unbounded call ran directly in the audit process. `add_years({{1,1,1},{0,0,0}},-1)` returns year zero; installed OTP calendar reports `{valid_date({0,1,1}),valid_date({-1,1,1}),valid_date({-1,1,0})} = {true,false,false}`. An ordinary negative-year adjustment within range (`{{4,2,29},...}` minus one year) terminates and clamps to February 28.

**Expected / actual:** Expected termination with a bounded out-of-range result/failure policy; no exact error class is promised by the current API, so none is prescribed here. Actual calls spin in the day-decrement recursion. Confidence high: repeated monitored observations, source transition, and inspected installed-calendar lower-bound guard agree. Future repair direction: validate representable year bounds before entering clamp recursion and choose an explicit compatibility-preserving failure policy; crossing the public calendar floor may require an API decision.

### ERL-CAL-002 — Duration composition rejects fractional-second datetime anchors

**Severity: Medium.** `datetime()` explicitly admits `second() | float()`, and `add_days/2` preserves a fractional second, but the shared duration composer crashes when its final offset conversion passes that float to the integer-only calendar Gregorian-seconds path. This breaks a typed public input and prevents parsed exact datetimes from being used with duration/interval APIs.

**Location and cause:** `src/iso8601.erl:40` defines the module’s `datetime()` seconds as integer or float; `70–76`, `162–164`, `197–232` expose arithmetic/application/resolution using that type. `524–528` preserves the seconds field while shifting days. In contrast `apply_duration_plist/3` always reaches `apply_offset/4` (`561–580`, `494–505`), which invokes `calendar:datetime_to_gregorian_seconds/1` with the float anchor and raises `function_clause`.

**Scale:** logical date-time arithmetic/composition unit, across `apply_duration/2` and anchored `interval_bounds/1`.

**Public reproduction:** With the same anchor `{{2017,1,1},{0,0,0.5}}`, `add_days(Anchor,1)` returns `{{2017,1,2},{0,0,0.5}}`, while `apply_duration(Anchor,"P1D")` raises `error:function_clause`. The parsed interval `parse_interval("2017-01-01T00:00:00.5Z/P1D")` succeeds, but `interval_bounds/1` on it raises the same error. Integer-second duration controls and the README start/duration example succeed. This is distinct from accepted Slice01 `ERL-DATE-005`: that finding is rounding fractional **hour/minute units during parsing** (`add_decimal/2`/`apply_offset/4`), whereas this finding is failure to compose an already represented fractional-second anchor; do not duplicate-count DATE005.

**Expected / actual:** The `datetime()`-typed anchor and unchanged fractional seconds should remain usable in day/duration composition; actual duration composition raises `function_clause`. Confidence high for input/result behavior. Recommendation: preserve the fractional seconds while applying integer calendar offsets, with a bounded and explicitly tested time arithmetic path. Public `parse_exact/1`’s separate spec mismatch (`calendar:datetime()` vs fractional output) remains the known Arc02 type-reconciliation obligation; this finding concerns runtime composition under the module’s own `datetime()` and `interval()` aliases.

### ERL-CAL-003 — Positive expanded years are misclassified or truncated in interval endpoints

**Severity: Medium.** `parse/1` accepts explicitly signed positive expanded years, but interval endpoint detection only treats four leading unsigned digits as a complete endpoint, and inherited-year extraction takes exactly the first four characters. An expanded start therefore makes an explicitly expanded end fail or makes an abbreviated month/day end inherit the wrong year.

**Location and cause:** `src/iso8601.erl:638–662` determines whether the right endpoint is abbreviated and recognizes only four unsigned leading digits; `664–680`, especially `extract_year/1` at `715–716`, reconstructs inherited endpoints using the first four raw characters. `parse_endpoint/1` uses `parse/1`, which accepts positive expanded representation as documented in README lines 177–184. The historical interval design likewise specified complete endpoints through existing `parse/1`; its status remains provenance, not standards authority.

**Scale:** interval public API/logical endpoint-classification unit.

**Public reproduction:** Standalone `parse("+0002007-02-15")` returns year 2007, and plain-year control `parse_interval("2007-02-15/03-14")` inherits end year 2007. But valid positive expanded start `parse_interval("+0002007-02-15/03-14")` returns end `{{0,3,14},{0,0,0}}`, and explicit full endpoint control `parse_interval("+0002007-02-15/+0002007-03-14")` raises `badarg`. The `+2007` four-digit signed candidate also demonstrates truncation (`{{200,3,14},...}`), but the finding does not rely on calling that representation valid; the `+0002007` public-documentation case is the valid discriminator.

**Expected / actual:** A complete signed positive year accepted by `parse/1` should stay complete in a full interval endpoint and in inherited year context; actual output truncates to year zero for abbreviated end and rejects explicit expanded end. Confidence high. Recommendation: classify signed positive-year prefixes consistently with `parse/1` and extract the complete year token before inheritance; preserve ordinary 4-digit controls and avoid changing the separate `parse_expanded/1` negative-year contract.

### ERL-CAL-004 — Abbreviated time end drops a zoned start’s explicit offset

**Severity: Medium.** A time-only end inherits the date but not the timezone from a valid zoned start. The resulting interval end differs by the start’s offset. The README promises inheritance of omitted leading endpoint components; the preserved interval design’s resolved decision explicitly includes timezone inheritance. This is an implementation-vs-repository-intent finding, not an external ISO-conformance claim.

**Location and cause:** `src/iso8601.erl:638–680` parses the start to normalized UTC, then for `{time_only,...}` `extract_date_part/1` (`711–712`) keeps only the date and reconstructs a timezone-free end string. The start’s raw zone is not appended before parsing the end.

**Scale:** interval public API/logical abbreviated endpoint-resolution unit.

**Public reproduction:** `parse_interval("2007-12-14T13:30:00+02:00/15:30:00")` followed by `interval_bounds/1` returns UTC bounds 11:30 and 15:30. Per the repository’s inheritance intent, omitted end zone inherits `+02:00`; the expected end is 13:30 UTC. An explicit-end control `.../15:30:00+02:00` yields 11:30/13:30 UTC, and a `Z`-start/time-only-end case yields same-day 13:30/15:30 UTC. This isolates the missing-zone case while confirming the end’s own explicit zone is normalized correctly.

**Expected / actual:** Start/end raw zone context is inherited when the end omits it; actual reconstruction discards it and treats end time as UTC. Confidence medium-high: exact public output plus source path reproduce; historical design §§5 and 7 record the resolved intent and current README says abbreviated ends inherit missing leading components, but the current README does not separately name timezone. Recommendation: preserve the starting zone token for abbreviated-end reconstruction, while leaving fully specified mixed-zone endpoints independently normalized. No ISO standards behavior beyond repository intent is asserted.

## Candidate disposition: reduced-precision zoned start

Fresh `parse_interval("2007-12-14T13:30+02:00/15:30:00")` raises `badarg`. The full-seconds counterpart succeeds and distinguishes this parser failure from inheritance. Source lines `299–387` only route a UTC-offset parse after seconds parsing; after minutes, the parser does not dispatch `+/-` to offset parsing. The observation is real, but there is no current README/test promise for this reduced-precision-plus-offset form, and the rejection occurs before interval inheritance. Disposition: retain as an Arc02/parser-scope note, not a Slice02 finding absent a current contract or independently authorized standards audit. CDC’s pre-handoff observation is separately recorded in the runlog and was not represented as fresh.

## Concrete clean checks

1. `add_time/4` carries 2017-12-31 23:59:59 + 1 second to 2018-01-01 00:00:00; `subtract_time/4` returns the same boundary for the matching subtraction control.
2. `add_days/2` crosses 2016-02-28 to leap day with its time unchanged.
3. Month/year clamping returns 2017-02-28 from 2017-01-31 +1 month and 2016-02-29 +1 year, matching explicit existing EUnit expectations; this does not assert inverse arithmetic.
4. `parse_duration/1` preserves signed component fields in sign/year/month/day/hour/minute/second order; `apply_duration/2` honors `-P1Y`, producing 2016 from 2017.
5. Sequential `P1M1D` from 2020-01-31 yields 2020-03-01 (February clamp then day addition), consistent with source’s documented component order; this is not a commutativity/inverse assertion.
6. All four interval forms parse; anchored start/duration bounds and negative duration/end bounds follow source behavior; duration-only bounds raises the documented `badarg` because it has no anchor.
7. Slash and legacy double-hyphen separators both parse; abbreviated day and UTC time-only cases inherit date components; canonical interval formatting returns the expected binary for slash-form and duration-only cases.
8. Malformed two-duration and three-part interval inputs raise `badarg`; explicit-end zone normalization control passes.
9. Positive expanded endpoint parsing works standalone as README documents; plain unsigned-year interval inheritance remains correct. The expanded-interval discrepancy is captured above rather than generalized to unrelated year forms.
10. The installed calendar lower-bound control confirms year zero valid and year -1 invalid, making the year-underflow recursion invariant explicit rather than inferred from timeout alone.
