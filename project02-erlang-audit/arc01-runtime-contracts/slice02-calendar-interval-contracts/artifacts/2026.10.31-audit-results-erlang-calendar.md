The refinement retains four stable findings: CAL001 remains Medium for boundary underflow, where the same month arithmetic has both a silent year-zero wrap and below-floor nontermination; CAL002 is High because an ordinary `parse_exact/1` result composes into a public `function_clause`; CAL003 is High because a public formatter-produced `+2007` endpoint is truncated/misclassified; and CAL004 is High because an ordinary zoned-start/time-only-end interval resolves two hours away from the repository’s documented and preserved inheritance intent. ## Findings

### ERL-CAL-001 — Month/year underflow wraps silently or does not terminate below calendar year zero

**Severity: Medium.** A valid year-1 input with an integer negative month/year adjustment crossing below year zero leaves the caller in unbounded recursion, rather than completing or failing in bounded time. The triggering boundary is narrow, but the synchronous API can consume a caller process indefinitely.

**Location and cause:** `src/iso8601.erl:509–520` computes `AY=(Y*12)+M+AM`, then uses truncating `(AY-1) div 12` and `AY rem 12`; `537–542` recursively decrements only the day while retaining the same year and month. For `AY=0`, truncating division maps the mathematical below-floor result to year0/month12, so a `Year < 0` guard alone would miss a silent invalid wrap. For a negative adjusted year, installed OTP28 `calendar:valid_date/1` at `/opt/homebrew/Cellar/erlang/28.1.1/lib/erlang/lib/stdlib-7.1/src/calendar.erl:862–883` rejects every year below zero (`valid_date1` requires `Y >= 0`); no day value can make the fixed year/month valid and recursion cannot terminate. The shared path is also reached by `apply_duration/2` and interval bound resolution.

**Scale:** logical arithmetic/duration unit, affecting `add_years/2`, `add_months/2`, and composed duration/interval calls.

**Public reproduction:** `add_months({{0,1,1},{0,0,0}},-1)` and `add_months({{1,1,1},{0,0,0}},-13)` both return `{{0,12,1},{0,0,0}}`, although their absolute-month target is year -1 December. `add_months({{1,1,1},{0,0,0}},-12)` returns year0 January and is the within-floor control. Separately, `add_years({{1,1,1},{0,0,0}},-2)`, `add_months({{1,1,1},{0,0,0}},-24)`, `apply_duration({{2017,1,1},{0,0,0}},"-P9999Y")`, and `interval_bounds(parse_interval("0001-01-01/-P2Y"))` were each executed in a monitored child with 250 ms timeout, `kill`, and confirmed monitor `DOWN`; each timed out. No potentially unbounded call ran directly in the audit process. `add_years({{1,1,1},{0,0,0}},-1)` returns year zero; installed OTP calendar reports `{valid_date({0,1,1}),valid_date({-1,1,1}),valid_date({-1,1,0})} = {true,false,false}`. An ordinary negative-year adjustment within range (`{{4,2,29},...}` minus one year) terminates and clamps to February 28.

**Expected / actual:** Expected behavior at the year-zero floor is unresolved in the public error contract; no exact out-of-range error class is prescribed here. Actual `AY=0` silently returns a different, calendar-valid date, while negative-year calls spin in day-decrement recursion. Confidence high: fresh exact values, monitored observations, source transition, and installed-calendar lower-bound guard agree. Severity remains Medium because the triggering dates are at the representable-year boundary and the policy for crossing it is unspecified, despite the serious hang/wrong-date consequence. Future repair direction: validate representable year bounds before month correction/clamp recursion and choose an explicit compatibility-preserving failure policy; crossing the public calendar floor may require an API decision.

### ERL-CAL-002 — Duration composition rejects fractional-second datetime anchors

**Severity: High.** `datetime()` explicitly admits `second() | float()`, and ordinary `parse_exact("2017-01-01")` returns a float second `0.0`. Applying a routine one-day duration to that parser-produced public value raises `function_clause`; the matched integer-second anchor succeeds. This is a realistic correctness failure in public API composition, not only an explicit fractional-literal edge case.

**Location and cause:** `src/iso8601.erl:40` defines the module’s `datetime()` seconds as integer or float; `70–76`, `192–196`, `197–232` expose arithmetic/application/resolution using that type. `524–528` preserves the seconds field while shifting days. In contrast `apply_duration_plist/3` always reaches `apply_offset/4` (`561–580`, `494–505`), which invokes `calendar:datetime_to_gregorian_seconds/1` with the float anchor and raises `function_clause` at the integer-only `calendar:time_to_seconds/1` leaf.

**Scale:** logical date-time arithmetic/composition unit, across `apply_duration/2` and anchored `interval_bounds/1`.

**Public reproduction:** `parse_exact("2017-01-01")` returns exactly `{{2017,1,1},{0,0,0.0}}`; `apply_duration/2` with that value and `"P1D"` raises `error:function_clause`, while integer anchor `{{2017,1,1},{0,0,0}}` returns `{{2017,1,2},{0,0,0}}`. Captured stack: `calendar:time_to_seconds({0,0,0.0})` line817 → `calendar:datetime_to_gregorian_seconds/1` line259 → `iso8601:apply_offset/4` line499. `interval_bounds(parse_interval("2017-01-01T00:00:00.0Z/P1D"))` raises the same leaf failure. An explicit `.5` anchor and `add_days/2` pass-through control confirm preservation versus composition. This is distinct from accepted Slice01 `ERL-DATE-005`: that finding is rounding fractional **hour/minute units during parsing** (`add_decimal/2`/`apply_offset/4`), whereas this finding is failure to compose a parser-produced fractional-second anchor; do not duplicate-count DATE005.

**Expected / actual:** The module-typed, parser-produced anchor should compose with a duration while preserving its fractional second; actual composition raises `function_clause`. Confidence high for input/result behavior and call path. Recommendation: preserve fractional seconds while applying integer calendar offsets, with a bounded and explicitly tested time arithmetic path. Public `parse_exact/1`’s separate spec mismatch (`calendar:datetime()` vs fractional output) remains the known Arc02 type-reconciliation obligation; this finding concerns runtime composition under the module’s own `datetime()` and `interval()` aliases.

### ERL-CAL-003 — Positive expanded years are misclassified or truncated in interval endpoints

**Severity: High.** `format_expanded/1` itself emits `+2007` for an ordinary positive year, and `parse/1` accepts that output. A formatter-produced start followed by an abbreviated endpoint returns year200, while an explicit signed end raises `badarg`; a valid seven-digit signed positive year also truncates to year0 when abbreviated. This is realistic data corruption in a public formatting/parsing/interval composition path.

**Location and cause:** `src/iso8601.erl:638–662` determines whether the right endpoint is abbreviated and recognizes only four unsigned leading digits; `664–680`, especially `extract_year/1` at `715–716`, reconstructs inherited endpoints using the first four raw characters. `parse_endpoint/1` uses `parse/1`, which accepts positive expanded representation as documented in README lines 177–184. The historical interval design likewise specified complete endpoints through existing `parse/1`; its status remains provenance, not standards authority.

**Scale:** interval public API/logical endpoint-classification unit.

**Public reproduction:** `format_expanded({{2007,2,15},{0,0,0}})` returns `<<"+2007-02-15T00:00:00Z">>` and `parse/1` accepts it. Starting an interval with that formatted value and abbreviated `03-14` returns end `{{200,3,14},{0,0,0}}`; an explicit `+2007-03-14` end raises `badarg`. The additional valid seven-digit case `+0002007-02-15/03-14` returns end year0, while full explicit endpoints raise `badarg`; unsigned `2007-02-15/03-14` remains year2007 control. The fresh evidence does not call `+2007` malformed; it establishes that a public formatter-produced spelling is misclassified/truncated.

**Expected / actual:** Signed-year endpoints produced by the public formatter and accepted by `parse/1` should retain their year in explicit and abbreviated interval contexts; actual output truncates/misclassifies or rejects them. Confidence high. Recommendation: classify signed positive-year prefixes consistently with `parse/1` and extract the complete year token before inheritance; preserve ordinary 4-digit controls and avoid changing the separate `parse_expanded/1` negative-year contract.

### ERL-CAL-004 — Abbreviated time end drops a zoned start’s explicit offset

**Severity: High.** For an ordinary valid zoned start and time-only end, bounds are two hours later than the repository’s documented abbreviated-component behavior and preserved timezone-inheritance decision imply. This is a material interval result error under a realistic operating pattern. The finding is repository-intent based, not an external ISO-conformance claim; that evidence limit lowers confidence, not consequence severity.

**Location and cause:** `src/iso8601.erl:638–680` parses the start to normalized UTC, then for `{time_only,...}` `extract_date_part/1` (`711–712`) keeps only the date and reconstructs a timezone-free end string. The start’s raw zone is not appended before parsing the end.

**Scale:** interval public API/logical abbreviated endpoint-resolution unit.

**Public reproduction:** `parse_interval("2007-12-14T13:30:00+02:00/15:30:00")` followed by `interval_bounds/1` returns UTC bounds 11:30 and 15:30. Under the README’s omitted-component inheritance promise and archived resolved timezone intent, the omitted end zone inherits `+02:00`; expected end is 13:30 UTC, so the observed bound is two hours later. An explicit-end control `.../15:30:00+02:00` yields 11:30/13:30 UTC, and a `Z`-start/time-only-end case yields same-day 13:30/15:30 UTC. A separate minute-precision `13:30+02:00/...` input raises `badarg` before inheritance and is separately dispositioned below; it does not weaken the full-seconds witness.

**Expected / actual:** Start/end raw zone context is inherited when the end omits it; actual reconstruction discards it and treats end time as UTC. Confidence medium-high: exact public output plus source path reproduce; historical design §§5 and 7 record the resolved intent and current README says abbreviated ends inherit missing leading components, but the current README does not separately name timezone. Severity High reflects the ordinary two-hour bounds error against that documented/preserved repository intent; this confidence caveat remains separate from consequence. Recommendation: preserve the starting zone token for abbreviated-end reconstruction, while leaving fully specified mixed-zone endpoints independently normalized. No ISO standards behavior beyond repository intent is asserted.

## Candidate disposition: reduced-precision zoned start

Fresh `parse_interval("2007-12-14T13:30+02:00/15:30:00")` raises `badarg`; the full-seconds counterpart succeeds and distinguishes parser failure from inheritance. Source lines `299–387` route UTC-offset parsing only after seconds parsing; after minutes, the parser does not dispatch `+/-` to offset parsing. The observation is real, but there is no current README/test promise for this reduced-precision-plus-offset form, and rejection occurs before interval inheritance. Disposition: retain as an Arc02/parser-scope candidate, not a Slice02 finding absent a current contract or independently authorized standards audit. CDC’s pre-handoff witness is separately attributed in the runlog and is not this fresh result.

## Zero-duration disposition

Fresh probes parse `P0D`, `PT0S`, and bare `P` to all-zero duration fields; apply each to an integer-second `datetime`; resolve date/zero-duration interval bounds; and serialize all three intervals. Every application/bounds control preserves the anchor. `format_interval/1` emits `2017-01-01T00:00:00Z/P` for each start/zero-duration input and `P` for duration-only. The archived implementation brief at `time-intervals-impl-prompt.md:118–132` explicitly says to omit zero components, always emit `P`, and emit `T` only when any time component is nonzero; current `format_duration/1` at source `721–744` follows this. This is preserved implementation intent and is not classified as a defect or as an ISO conformance conclusion. Existing EUnit timestamp-dispatch controls at `test/iso8601_tests.erl:334–341` remain retained evidence; they were not rerun during this refinement.

## Concrete clean checks

1. `add_time/4` carries 2017-12-31 23:59:59 + 1 second to 2018-01-01 00:00:00; `subtract_time/4` returns the same boundary for the matching subtraction control.
2. `add_days/2` crosses 2016-02-28 to leap day with its time unchanged.
3. Month/year clamping returns 2017-02-28 from 2017-01-31 +1 month and 2016-02-29 +1 year, matching explicit existing EUnit expectations; this does not assert inverse arithmetic.
4. `parse_duration/1` preserves signed component fields in sign/year/month/day/hour/minute/second order; `apply_duration/2` honors `-P1Y`, producing 2016 from 2017.
5. Sequential `P1M1D` from 2020-01-31 yields 2020-03-01 (February clamp then day addition), consistent with source’s documented component order; this is not a commutativity/inverse assertion.
6. All four interval forms parse; anchored start/duration bounds and negative duration/end bounds follow source behavior; duration-only bounds raises the documented `badarg` because it has no anchor.
7. Slash and legacy double-hyphen separators both parse; abbreviated day and UTC time-only cases inherit date components; canonical interval formatting returns the expected binary for slash-form and duration-only cases.
8. Malformed two-duration and three-part interval inputs raise `badarg`; explicit-end zone normalization control passes.
9. Positive expanded endpoint parsing works standalone as README documents; plain unsigned-year interval inheritance remains correct. The expanded-interval discrepancy is captured above rather than generalized to unrelated year forms.
10. Successful floor/calendar controls: `add_years({{1,1,1},{0,0,0}},-1)` returns year0 January; `add_months({{1,1,1},{0,0,0}},-12)` also returns year0 January; installed calendar validity is `{true,false,false}` for year0 Jan / year−1 Jan / year−1 Jan day0.
11. Zero durations `P0D`/`PT0S` and historical bare `P` parse, apply, resolve bounds, and format consistently with the preserved zero-component omission rule.
