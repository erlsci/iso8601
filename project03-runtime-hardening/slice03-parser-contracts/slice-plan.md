## Binding recipe and caller boundaries

**Input bytes.** All FOUR public specs declare iodata: parse/1, parse_exact/1, parse_expanded/1 (baseline131–157), parse_interval/1 (207–222). Normalize each boundary with binary_to_list(iolist_to_binary(Input)) via one small private helper or equivalent shared conversion, before existing date/interval dispatch. This supports nested byte lists, binary fragments and a binary improper tail. Do not use lists:flatten (does not flatten binary fragments), Unicode conversion, atom conversion or a blanket catch. Invalid non-iodata naturally raises error:badarg from the BIF; retain malformed-syntax rejection after normalization. parse_duration/apply_duration retain existing string contracts and representation. The internal parse_endpoint calls ordinary/exact public parsing, so interval calendar validation follows automatically; interval input must normalize before split_interval/is_duration_str, including duration-only forms. No new parser accumulator shape/type/spec is needed. New helper annotations are optional; if present, validators must accept raw invalid integer fields and negative years they examine rather than already-valid month/day types. Existing unrelated old annotations stay unchanged absent a reproduced blocker.

**Calendar fields.** make_date/4's undefined-week branch (491–494) currently accepts Year<=0 without validation. Reuse days_in_months_for_year/is_leap_year (427–438), which correctly handle zero and negative divisible years. Check bounds before lists:nth/nthtail to avoid wrong exceptions. Recommended private boolean predicate on the raw {Year,Month,Day}; false leads to explicit error(badarg) in make_date. Valid negative dates and zero/negative leap dates survive, including omitted year/month defaults and ordinal results. Do not route negative dates through calendar:valid_date or conversion whose supported signed range differs across OTP28/29. Do not normalize an invalid raw date via a timezone/fraction before rejecting it.
